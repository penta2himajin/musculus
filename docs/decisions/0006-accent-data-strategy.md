# ADR-0006: アクセント(韻律)データ戦略 — 規則 + ユーザ上書き + tdmelodic 由来辞書

- ステータス: 採用
- 日付: 2026-09-14
- 関連: ADR-0002/0004/0005、docs/benchmarks/accent/ja-report.md、docs/model-licenses.md、docs/evaluation.md

## 背景

listening 評価でアクセントの欠陥が確定した(「1,200」= 現行 `HLLHH` vs 期待 `HHLHH`/`LLLHH`、原因は特殊拍ではなく**アクセント推定**)。さらに listener から「**標準的(アナウンサー的)な発音を目標にしたい。そういった情報をベースに韻律を組むのが良いのでは**」という方針提案があった。

調査の結果、**使える資源と使えない資源が明確に分かれた**(docs/model-licenses.md に記録):

| 資源 | ライセンス | 可否 |
|---|---|---|
| **tdmelodic**(PKSHATechnology-Research、日本語アクセント辞書生成) | **BSD-3-Clause** | ✅ 商用可。ニューラル推定で大語彙アクセント辞書を生成(Tachibana & Katayama, ICASSP 2020) |
| **tdmelodic_openjtalk**(sarulab-speech) | 未確認 | ⚠️ OpenJTalk 辞書化の実装。**jpreprocess と直結しうる** |
| **UniDic**(現代書き言葉 Ver.2.x+ / 話し言葉 Ver.2.2.x+) | **GPLv2 / LGPLv2.1 / 修正BSD のトリプル** | ✅ 商用可。KAKEN 19K13173 でクラウドソーシングによる**アクセント情報付与**が行われた |
| **UniDic非コアデータ** | **Apache-2.0**(2019.08 に MIT から変更) | ✅ 商用可。ただし確認したページの公開物はカタカナ略語・複合語分割リストで、**アクセントデータの所在は要確認** |
| **koniwa(声庭)** | アノテーション **CC0**、プログラム **Apache-2.0**、音声 CC BY/PD | ✅ **韻律アノテーション付き音声**。L3 gold・検証コーパスに使える |
| **OJAD**(東大) | 教育・学術研究目的に限定。**「営利活動を目的とした企業の研究開発での利用はお控えください」** | ❌ 製品では使えない |
| **NHK 日本語発音アクセント新辞典** | 著作物 | ❌ データ同梱不可。**公開された“原則”**(研究記事)は規則設計の根拠として参照可 |

## 決定

**アクセント(韻律)は多層のソースから組み、データは同梱せずユーザが取得する。**

1. **規則層(既定)**: 現行フロントエンド + 文献に基づく規則(数詞複合語の核消失、-sen の penultimate、分離可能な小句、助数詞「円」支配、1 句 1 核)。文献の“原則”のみを実装し、辞書データは複製しない
2. **上書き層(ユーザ所有)**: 語・句ごとに H/L を指定する表。固有名詞・商品名・話者固有の揺れを吸収する。**「正解が一つでない」ことを設計に反映**し、どの型を採るかは話者が持つ
3. **標準アクセント辞書層(tdmelodic 由来)** ← 今回の提案の本命
   - **tdmelodic(BSD-3)** で UniDic + NEologd から大語彙アクセント辞書を生成し、**OpenJTalk/jpreprocess 互換の辞書**(語見出し + 読み + アクセント型 + モーラ数)として組み込む
   - これにより**アクセント推定を“ソース”で直す**。我々のトーン生成はラベルに忠実であることを実測済みなので、ラベルが正しくなれば H/L も正しくなる
   - setup スクリプトで取得(Python/torch が必要)。**musculus は重み・辞書を同梱しない**原則を維持
4. **検証層**: L3 アクセント gold を **koniwa(CC0 アノテーション)** と自前アノテーションで整備し、CI gate にする。不変条件「**1 アクセント句に核は最大 1 つ**」も自動テスト化

## 理由

- 「標準的(アナウンサー的)な発音」を目標にするなら、**NHK 辞書の第一形に相当する標準アクセントを、許諾されたデータで再現する**のが最短。tdmelodic はまさにその目的の研究実装で、BSD-3 で商用可
- jpreprocess は OpenJTalk 系の辞書形式を使うため、**tdmelodic の OpenJTalk 版がそのまま接続可能**な見込みが高い(要検証)
- OJAD は明示的に企業利用を避けるよう求めており、NHK 辞書は著作物。**これらを使わずに同等の目標へ到達できる経路が存在する**ことが調査で確認できた
- 上書き層を併せて持つことで、標準形と話者固有形の**両方を表現**できる(現行素性は H/L 2 値で、listener の 3 核パターン `HHLLHHHL` も表現可能と確認済み)

## 結果として生じる作業

1. **短期(安価)**: 上書き層の実装(`--accent <file>` + `AccentTable`)、アクセントレポートへの gate 組込み
2. **中期**: tdmelodic + tdmelodic_openjtalk の検証(Python 環境、辞書生成、jpreprocess への組み込み経路、生成辞書のライセンス表記)。`sarulab-speech/tdmelodic_openjtalk` のライセンス確認
3. **中期**: 規則層の拡張(数詞複合語の核消失、助数詞支配)— 各規則を聴取で検証
4. **検証整備**: koniwa から L3 アクセント gold を作る手順の確立(CC0 アノテーションの形式確認)

## 未確認事項(次に潰す)

- `tdmelodic_openjtalk` のライセンス
- jpreprocess が**外部ビルド辞書**を受け入れるか(現行は同梱の NAIST-jdic ベース。`jpreprocess-dictionary` のビルドツールと特徴量の確認が必要)
- アクセント情報付き UniDic データの公開場所とライセンス(KAKEN 19K13173 の成果物)
- koniwa アノテーションのスキーマにアクセント(モーラ H/L または核位置)が含まれるか
